# 13 - Hardware-Software Integration and Processor Selection

Status: DRAFT (verification pass). Evidence labels: **[S]** from a cited source, **[C]** computed by a script in `scripts/`,
**[E]** engineering estimate with a stated verification route. Nothing here is a measured result on the target hardware.

## 1. Principle: three execution domains

| Domain | What runs there | Why |
|---|---|---|
| Hardware data plane (FPGA fabric, later ASIC logic) | OFDM modem, LDPC, framing, encryption, video encode/decode, slice packetiser, frame-timeline sequencer, timestamp unit | Deadlines of microseconds to one slice (about 1 to 2 ms); the rates (tens of Mbit/s, 10 MB/s of video) are too high for software at low power |
| Hard real-time control core(s) | MAC scheduling, link adaptation, rate-control retarget, calibration loops, thermal/VSWR loops, UART protocols, logging | Deterministic response (interrupt to action in 100 us or less), small and low-power |
| Application core (Linux, optional, power-gated on the air unit) | HAL services, configuration web/API, OTA update, recording, OSD, ground-unit user interface | Needs a full OS and drivers; no hard deadlines |

The data plane keeps running if both processors stall (SW-001): the **frame-timeline sequencer** executes a table of events (TX/RX enable, PA
enable, switch, gain step, PLL profile, preamble, slice slot) loaded by the real-time core one or more frames ahead. The CPU never sits
in the microsecond path (a hop or a turn-around is triggered by the sequencer, not by an SPI write from software).

## 2. Control-plane workload (air unit, 1080p120 worst case)

|---|---|---|---|---|

| Per-slice rate-control retarget | 960 | 4,000 | 3.8 | VID-006, 8 slices per frame at 120 fps |

| Logging into the ring buffer | 1,000 | 1,500 | 1.5 | SW-005 |

| **Total, real-time core, hardware assist for DPD matrix and crypto** | | | **34.4** | |

| Function kept out of the CPU | Rate per s | Cycles per event | Mcycles/s | Basis |
|---|---|---|---|---|
| DPD correlation matrix formed in software | 10 | 7,372,800 | 73.7 | 4096 samples x 15 x 15 complex MACs; put in a hardware accumulator instead |
| Link encryption in software | 10,000,000 | 4 | 40.0 | SEC-002; use the hardware block instead |

| Core clock MHz | Load, hardware assist | Load, DPD matrix in software | Load, DPD and crypto in software |
|---|---|---|---|
| 200 | 17% | 54% | 74% |
| 300 | 11% | 36% | 49% |
| 400 | 9% | 27% | 37% |
| 600 | 6% | 18% | 25% |

Reading the table:

- With the DPD correlation matrix and the encryption in hardware, the real-time work is about 34 Mcycles/s; a 300 MHz core is 11% loaded,
  which leaves room for worst-case execution times several times larger than assumed.
- Forming the DPD matrix in software costs 74 Mcycles/s (4096 samples x 15 x 15 complex multiply-accumulates at 8 cycles each) and software
  encryption another 40 Mcycles/s: together they take a 300 MHz core to 49%. Both are therefore specified as hardware blocks (HSI-004).
- The largest software item is MAVLink/MSP byte handling (15 Mcycles/s at 3 Mbaud); it should be DMA-driven with per-message parsing.
- Numerical note [E]: the DPD solve on 15 complex coefficients needs a conditioned method (regularised Cholesky or QR) and probably double
  precision or a careful single-precision implementation; to be checked by simulation before choosing a core without a double-precision FPU.

## 3. Two-phase platform plan (processing platforms)

The decision rule requested for the project: **phase A runs on low-cost evaluation boards; phase B moves to a custom board with the controllers
that the design actually targets.** The plan below applies it to the three processing functions.

### 3.1 Phase A - low-cost evaluation boards

Purpose: prove the waveform, the MAC, the calibration and rate-control logic, and measure real latency components, using boards that need no
hardware design. The latency measured in phase A includes inter-board links and is **not** a product number; the budget in `02` is validated
in phase B (HSI-010).

| Function | Candidate evaluation platform | Facts found | Limits and risks |
|---|---|---|---|
| PHY/MAC bring-up (waveform, framing, TDD, calibration hooks) | ADALM-PLUTO (AD9363 + Zynq Z-7010: one Cortex-A9 at 667 MHz, 28k logic cells, 80 DSP slices, 512 MB DDR3L) [S: [ADI Pluto page](https://analogdevicesinc.github.io/documentation/solutions/platforms/pluto/index.html)] | RF 325 MHz to 3.8 GHz guaranteed, 70 MHz to 6 GHz only with the firmware modification; 20 MHz instantaneous bandwidth | 28k logic cells is small for LDPC plus modem plus framing [E, synthesis needed]; 5.8 GHz outside the guaranteed range; no DPD or high power; best for 5/10/20 MHz modem and MAC prototyping at 2.4 GHz |
| PHY/MAC with video encoder in one device | AMD Kria K26 SOM / KV260 (Zynq UltraScale+ XCK26) [S: [power figures: typical 7.5 W, maximum 15 W](https://www.digikey.ca/en/product-highlight/x/xilinx/kv260-vision-ai-starter-kit)] | Quad Cortex-A53 plus real-time cores plus programmable logic; VCU video codec present on EV-class devices [S: AMD describes a hardened VCU for 4K60 encode/decode; **whether the XCK26 includes it was not confirmed by the search**] | 7.5 W typical is above the 8 W prototype ceiling of PWR-003 once an RF board is added [C: 7.5 + transceiver 1.5 W = 9 W]; no FMC connector on KV260 [E, check the board]; VCU latency and power figures were not found (the AMD low-latency reference designs exist but give no number in the search results) |
| PHY/MAC with the ADI-supported RF boards | Zynq UltraScale+ development kits (for example ZCU104 with EV device) plus FMCOMMS-class AD9361 boards, or ADRV9002 evaluation boards | ADI HDL and Linux drivers exist (`reference/sdr-phy/hdl`, `plutosdr-fw`) | Not low-cost; use only if the low-cost options cannot hold the design |
| Camera/encoder baseline (P0) | IP-camera SoC boards running OpenIPC/waybeam (SigmaStar, HiSilicon) | Working today; camera half p50 80-95 ms measured by OpenIPC's own tool [S: source review S-3] | Encoder cannot enforce per-frame size caps and has hidden limits [S: S-4, S-5]; baseline only |
| Ground decode/display (P0) | Rockchip RK3566 (Radxa Zero 3W class) or Raspberry Pi 5 class boards; RK3588 boards | RK3588 encoder claimed up to 4K120 and RK3566 1080p60 HEVC [S: search summaries, vendor/community claims]; mainline Linux RK3588 has decode but encoder support was reported missing | Power figures not found; decode latency to be measured; display scan-out control is the real issue (VID-018) |
| Real-time control | The real-time cores of the Zynq parts (Cortex-R5F on UltraScale+; on Z-7010 only the A9) | R5F cores are present on the UltraScale+ parts [E: from AMD family documents, not re-read here] | On Pluto the control loops run on the A9 under Linux (PREEMPT_RT) or in the fabric: acceptable for phase A, not for the product |

Phase A radio configurations (PRO-007): A1 two PlutoSDR-class radios, video 2.4 GHz plus uplink 915 MHz, inside the guaranteed range; A2 AD9361/ADRV9002 evaluation pair, video 5.8 GHz plus uplink 2.4 GHz; A3 video pipeline on a K26-class board with a Rockchip/Pi-class ground decoder (`07` T-19).

Phase A exit criteria: modem and MAC working over the air at 5/10/20 MHz; per-stage timestamps from every block (LAT-004); calibration loops
(IQ, LO, power control, VSWR sensing with an external coupler) demonstrated on bench; measured, not assumed, values for the open items in `12`
(turn-around time, hop time, encoder first-slice latency).

### 3.2 Phase B - custom board with the target controllers

Purpose: meet size, weight, power and latency targets with production-intent parts, before the ASIC exists.

| Function | Target controller (phase B) | Reason and gate |
|---|---|---|
| Transceiver | ADRV9002-class (30 MHz to 6 GHz, up to 40 MHz, integrated DPD, demonstrated 13 us hop frames) [S] | Closest to RF-006, RF-009, CAL-005 [S/E]; verify power and calibration scheduling on the evaluation board first |
| PHY, MAC, video data plane | Zynq UltraScale+ EV-class device on a custom board (module or bare device), with a custom slice encoder replacing the hard codec only if the VCU latency fails VID-007 | One device holds modem, FEC, codec, sequencer and the processors; gate: air-unit input power within SYS-005 at 25 dBm (3.5 W) is **not** achievable with this device [C: the device alone is 7.5 W typical in the K26 case], so phase B is a function-and-latency target, not the SYS-005 power target |
| Real-time control | The device's Cortex-R5F cores (bare-metal or Zephyr/FreeRTOS), Linux on the A53 cluster only on the ground unit and as an option on the air unit | Meets the load budget in section 2 with a wide margin |
| Ground unit | Same FPGA device or an SBC-class SoC with hardware HEVC/AVC decode, plus a display controller with a steerable pixel clock | VID-015, VID-018 |

Phase B exit criteria: G2G budget of `02` measured on the custom board (SYS-002 at 30 ms, then SYS-001 target within 20%); thermal and mass
measured; production-intent connector and FEM choices frozen.

### 3.3 Phase C - ASIC processors (not before phase B exit)

| Option | Description | Pros | Cons |
|---|---|---|---|
| A | Two or more real-time cores (Cortex-R5F or M7 class, 300 to 400 MHz) plus one application core (Cortex-A53/A55 class, power-gated) | Mature tool and OS support; same architecture as the phase B device (software moves unchanged); the real-time cores cost little power | Licence and royalty costs; the application core dominates the processor power if left on |
| B | RISC-V: 32-bit real-time cores with FPU (open cores such as the CORE-V family or Ibex-class) plus one Linux-capable 64-bit core (CVA6 class) | No licence fee; freedom to add instructions (for example for LDPC/DPD helpers); lower core power possible | Software and tool maturity (RTOS ports, safety certification, WCET tools) is lower; the FPGA prototype runs ARM cores, so software must be ported and re-verified; support risk |
| C | Real-time cores only (no application core) on the air unit; Linux on the ground unit or on a companion board | Lowest power and fastest boot (no Linux in the boot path); smaller area | No on-board web/API; configuration over UART/USB or through the ground unit; OTA update logic in the real-time firmware |

Recommendation: **A for the first ASIC (continuity with phase B) with C as the air-unit default configuration** (the application core is optional and
power-gated), keeping B as a cost/IP-freedom study (T-18 in `07`).

## 4. Processor power profile

Anchors found [S]: a single Cortex-A53 core at 1 GHz stays under 500 mW and a four-core A53 load at 1.4 GHz is about 880 mW on the core rail
in TI's AM62 documentation (system-level figures; the process node was not confirmed) ([TI SPRAD43 as found by search](https://docs.ampnuts.ru/ti.com.datasheet/AM625/Application_note_SPRAD43.PDF)); Arm M4 dynamic power of 33 uW/MHz at 90 nm LP and an M7 estimate of
50 to 75% more than the M4 ([AnandTech](https://anandtech.com/print/8542/cortexm7-launches-embedded-iot-and-wearables)); LPDDR4 interface energy of about 3 pJ/bit excluding core, controller and PHY power
([JEDEC-related slide as found by search](https://pc.watch.impress.co.jp/img/pcw/docs/1197/355/JEDEC.pdf)).

| Item | Estimate [E] | Derivation |
|---|---|---|
| Real-time core, 300 MHz, ASIC 28 nm class | about 5 to 20 mW including TCM/cache | 33 uW/MHz (90 nm) x 1.5 to 1.75 for an M7-class core, divided by an assumed 3x for the node, times 300 MHz = 5 to 6 mW; doubled for memory and bus; the node scaling is an assumption |
| Application core, A53-class, 400 MHz | about 150 mW running, 0 mW gated | scaling the 500 mW at 1 GHz figure roughly with frequency and voltage; duty-cycled at 20% gives about 30 mW average |
| DRAM interface, 1 GB/s video traffic | about 25 mW interface plus controller/PHY/refresh [E] | 1 GB/s x 8 bit x 3 pJ = 24 mW; core and PHY not included, so the 0.3 W memory line in `02` is a budget, not a derived value |
| Processor subsystem allocation (ASIC) | 100 mW running, 40 mW in sleep with Remote ID alive (target) | allocation inside the 0.7 W baseband line of `02` section 3 |

Consequences [E]:

1. The processor subsystem can be kept to about 100 mW only if the application core is power-gated; a permanently running four-core A53
   cluster (about 0.9 W in the anchor above) would exceed the entire 0.7 W baseband allocation (SYS-005 budget in `02`).
2. In the FPGA phases (A and B) the power is dominated by the fabric and the SOM (7.5 W typical in the K26 case), so no processor choice
   changes it; the processor decision matters for the ASIC.
3. Boot: Linux boot on an A-class core is typically several seconds [E, not measured here]; a real-time core with bare-metal or RTOS
   firmware boots in well under a second [E]. PWR-002 (video in 3 s) is therefore specified for the real-time path only (HSI-007).

## 5. Hardware-software interfaces

| Interface | Content | Timing requirement |
|---|---|---|
| Register map and sequencer table | Frame-timeline events, modem configuration, PHY profiles, calibration table pointers | Table for frame N+2 committed before frame N+1 starts; double-buffered, no partial updates |
| Timestamp unit | One 64-bit free-running counter at 200 MHz or faster (5 ns), latched at every pipeline stage boundary | All stages stamp the same counter (LAT-004); resolution 5 ns or better |
| DMA and ring buffers | Video slices, telemetry, logs, calibration capture buffers | Descriptor rings in shared memory with single-writer ownership; no CPU copies of video |
| Interrupts | Slice-complete, feedback-received, frame-start, thermal alarm, PA fault, sync-lost | Real-time core response (entry to first instruction of the handler) 5 us or less at 300 MHz [E]; handler work bounded |
| RF control | SPI/pin interface to the transceiver and FEM (bias, enable, gain steps, temperature, power detector) | Hop and turn-around via pins or profile triggers from the sequencer; SPI used only for slow updates |
| Inter-processor communication | Real-time core to application core: mailboxes plus shared memory (OpenAMP/RPMsg style on Zynq) | No real-time guarantee needed; no blocking call from the real-time side |
| Host interfaces | UART (MSP/MAVLink), USB, CAN-FD | DMA with per-message parsing |
| Debug and trace | Trace port with the stage timestamps, JTAG, UART console | Non-intrusive; on in all phases |

## 6. Boot, update and failure behaviour

1. Boot ROM verifies the signed real-time firmware and the FPGA bitstream (SEC-003), starts the real-time core, loads the sequencer and
   the modem; video starts without waiting for the application core (target 1.5 s, requirement 3 s: HSI-007).
2. The application core boots in the background; its absence or failure does not stop the link (SW-001).
3. Update: A/B images with rollback for the real-time firmware and bitstream; application-core image separately (SW-004).
4. Watchdogs: hardware watchdog per processor; the sequencer detects a stalled control core (no table update for two frames) and falls
   back to a safe schedule (lowest MCS, reduced power, continue video) rather than stopping.
5. Memory protection on the real-time core (MPU) between the control loops and the protocol tasks.

## 7. Verification of the hardware-software boundary

| Method | What it checks |
|---|---|
| Bit-accurate model versus RTL (`TG-PHY`) | The modem and FEC |
| Instruction-set simulation or QEMU plus RTL co-simulation (Verilator) | Firmware against the register map before silicon |
| Hardware-in-the-loop rig with channel emulator | Timing of the control loops against the sequencer |
| Worst-case execution time measurement on the target core with the trace port | The cycle counts in section 2 (replace the estimates) |
| Fault injection | Stalled core, corrupted table, thermal and PA fault paths |
| Load test | Real-time core load stays at 50% or less at the worst case (HSI-005) |
