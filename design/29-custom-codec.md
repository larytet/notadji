# 29 - Custom Slice-Based Video Encoder and Decoder

Plan entry: module 29 of `spec/18-development-plan.md`, class XL, data plane. Requirements: VID-027 (the video codec may be replaced by a project-specific codec that uses the same slice interface, rate-control interface, loss recovery and timestamp taps, so that it is a selectable profile and not a second architecture), VID-003 (codec-agnostic at slice level), VID-004 (at least 8 slices per 1080p frame, each independently decodable: no intra, motion-vector or entropy-context dependency across slice boundaries), VID-005 and VID-021 (no I-frames in steady state, rolling refresh, reactive slice refresh), VID-006 (per-slice budget, no slice above 105% of it, verified on the bitstream), VID-023 (foveation map as a per-block QP offset, the decoder needs no change), VID-017 (no royalty exposure). Plan test reference: TG-VID of `08`.

**What this module is and is not.** It is research-level work, as the plan says. What is delivered: (1) a **reference model** of the codec in software (`fw/29-codec/codec.py`: encoder and decoder, integer arithmetic where the encoder and the decoder have to agree), with measured properties: slice independence, the hard rate bound, reactive refresh, foveation, and a measured **rate-distortion comparison with x264** (installed on the development machine) on the same content; (2) an **RTL kernel** that the codec's hardware version would need first: the 8 x 8 transform and the quantiser, bit-exact against the model. Not delivered: an RTL encoder or decoder (motion search, mode decision, entropy coder, rate control) and a measured result on real flight video. The expectation, to be checked by the comparison, is that a simple codec built for slice independence and hardware simplicity is **less efficient than x264**; whether the other properties (native slice independence, quality degrading by slice, hard budget, no royalties, sub-frame latency) are worth the bit-rate cost is a decision for the project, and the measured gap is the input to it.

## 1. Codec definition (profile "SL1")

- **Picture**: 8-bit luma (chroma is open: the same tools apply to 4:2:0 chroma at half resolution, and the comparisons here are luma only), width and height multiples of 16, `S` slices of equal height (a multiple of 16 rows), each coded from its own bit string.
- **Block**: 8 x 8, raster order inside the slice; a macroblock is 16 x 16 (four blocks) and carries an optional QP offset.
- **Modes per block**: skip (copy of the previous reconstructed frame at the same place), inter (an integer motion vector, search range +/-8, the referenced area clipped to the **same slice rows of the previous frame**, residual), intra (DC prediction from the reconstructed left and top neighbours **inside the slice**, 128 if none, residual). Intra slices (type I) have intra blocks only.
- **Transform**: 8 x 8 Walsh-Hadamard (sequency order), `R = H X H` with `H` the 8 x 8 Hadamard matrix with entries +/-1; `H H = 8 I`, so `H R H = 64 X` and the transform is **exactly invertible in integers** without multiplications (the inverse adds and then `(. + 32) >> 6`). Chosen for hardware simplicity and exactness; its coding gain is below that of the DCT (open item: an integer DCT).
- **Quantisation**: step `s[qp][i][j] = round(8 x 0.625 x 2^(qp/6) x (1 + 0.05 (i + j)))` (the factor 8 is the gain of the unnormalised transform; the weighting is a mild frequency weighting), `qp` 0 to 51; level `= sign(c) ((|c| r + f) >> 16)` with `r = round(65536 / s)` and the rounding offset `f` 29491 (0.45) for intra and 21845 (1/3) for inter blocks; dequantisation `c' = level s`. The encoder holds the same reconstruction as the decoder (closed loop), so there is no drift between them.
- **Bitstream of a slice** (bit writer, Exp-Golomb codes `ue`, `se`): header: type (1 bit), `qp` (6 bits), `has_dqp` (1 bit); per macroblock `se(dqp)` when `has_dqp`; per block in P slices `ue(mode)` (0 skip, 1 inter, 2 intra); for inter `se(mvx - pred_x)`, `se(mvy - pred_y)` (prediction: the previous inter vector in the slice, (0, 0) at the start); then for non-skip blocks `ue(nnz)` (0 to 64) and for each non-zero coefficient in scan order `ue(run)`, `se(level)`; the slice ends with a stop bit `1` and zero padding to a byte. There is no state carried from one slice to the next.
- **Rate control** (VID-006): for every slice the encoder searches the smallest `qp` whose coded size is within the budget (bisection over `qp`, each probe is a full encode of the slice); if `qp` 51 still does not fit, the highest-frequency coefficients are dropped until it does (down to an all-skip slice, a few bytes). The bound is therefore met by construction whenever the budget exceeds the size of an all-skip slice. A fixed-`qp` mode is used for the rate-distortion curves.
- **Foveation** (VID-023): a map (centre, size, falloff width, strength) gives each macroblock a QP offset `dqp = round(strength x smoothstep)` coded in the bitstream, so the decoder needs no change.
- **Loss handling**: a decoder that misses a slice conceals it by copying the same area of the previous frame; the encoder, told which slice indices were lost (module 28's refresh path), codes those indices as type I in the next frame (VID-021). A rolling wave (one slice index per frame, period of at most 60 frames) refreshes every slice regularly (VID-005).

## 2. RTL kernel

`wht8x8` (forward and inverse by a flag): input 64 samples per block in raster order (9-bit signed residual for the forward direction, 16-bit coefficients for the inverse), one sample per clock; row pass, transposition memory, column pass; output 64 values in raster order (15-bit coefficients forward; 9-bit residual after `(. + 32) >> 6` inverse). `quant`: the combinational quantiser of section 1 for one coefficient with the step reciprocal `r` and the rounding offset `f` as inputs (the tables are generated by the firmware and written by the caller), one coefficient per clock. Bit-exact against the model. Throughput: 1080p60 needs 1.94 million blocks per second; one block takes about 140 clocks in `wht8x8` (64 in, pipelined 64 out, 8 pass latency), so one instance at 200 MHz gives 1.4 million blocks per second: two instances for luma (a single instance for the 4:2:0 chroma on top needs a third).

## 3. Test plan

| ID | Test | Pass criterion |
|---|---|---|
| T29-01 | Transform | `wht8x8` (RTL) equals the model for random blocks in both directions, including extreme values (+/-255 residuals); forward followed by inverse (no quantisation) returns the input exactly; `quant` equals the model for random coefficients, steps and offsets |
| T29-02 | Closed loop | 24 frames of the test sequence (panning and zooming crops of real photographs with sensor noise), 8 slices, fixed `qp`, foveation on and off, with refresh waves: the decoder's reconstruction equals the encoder's, bit for bit, in every frame |
| T29-03 | Slice independence | Any subset of the slices of a frame removed from the bitstream (single slices, half the slices, all but one): every remaining slice decodes to exactly the reconstruction of the full decode (when the reference frame is the same) and no parse of one slice touches another; corrupting the bytes of one slice leaves the others untouched |
| T29-04 | Rate bound | Budgets from 150 to 6000 bytes per slice (about 0.03 to 1.2 bit per pixel at 8 slices of 320 x 32): no slice exceeds its budget (hard bound, 105% allowed) whenever the budget is above the all-skip size; the achieved size over budget distribution is reported |
| T29-05 | Rate and distortion | PSNR against bit rate for SL1 (P frames, one I frame at the start, rolling wave) and for x264 (`libx264`, `-tune zerolatency`, 8 slices, no B-frames, constant `qp` swept) on the same sequence; the bit rate at equal PSNR (36 dB and 40 dB by interpolation) and the ratio are reported; SL1 with intra only and P against each other. No pass criterion on efficiency (the point is the measured gap); SL1 must reach 36 dB at a bit rate within 3 bit per pixel (a sanity bound) |
| T29-06 | Reactive refresh | One slice of one frame lost: without refresh the concealment error persists and grows with motion; with the refresh path the slice is intra in the next frame and its PSNR returns to within 1 dB of the loss-free value in that frame; the rate cost of the refresh over 100 frames at 5% slice loss is reported against a loss-free run |
| T29-07 | Foveation | A map with the high-quality region at the centre: PSNR in the region against PSNR in the periphery, and the bits saved at equal region PSNR against the uniform case (the 20 to 48% of `14` is an estimate [C/E]) |
| T29-08 | Complexity | Operation counts per pixel of the encoder (transform, quantisation, motion search with the +/-8 full search, rate-control re-encodes) and of the decoder; the hardware cost estimate for 1080p60; the speed of the Python model is reported but is not a measure of anything |
| L-29, S-29 | Lint and synthesis | RTL `-Wall` clean; no latches; counts recorded |

## 5. Open items

- Everything that makes a codec competitive: an integer DCT, better intra prediction, sub-pixel motion, context-adaptive entropy coding, in-loop filtering, chroma, B-frames are out of scope of a first reference; the measured gap to x264 says how much they matter.
- The RTL encoder and decoder (motion search, mode decision, entropy coder, rate control with the one-slice buffer) are not designed; the rate-control search of the model re-encodes a slice several times, which hardware cannot do: a hardware version needs a predictive `qp` choice with the truncation as the safety net.
- Real flight video (the test content is a synthetic motion over photographs), subjective quality, error resilience beyond slice loss, audio (VID-019).
- Not run on a target core.
