# 13 - LDPC Encoder

Plan entry: module 13 of `spec/18-development-plan.md`, class M, data plane. Requirements: PHY-005 (LDPC, code rates 1/2, 2/3, 3/4, 5/6; codeword length 648 bits in race mode, 1944 bits in cruise mode; slice-aligned codeword packing), PHY-015 (throughput target 155 Mbit/s of information, which the encoder must also meet), trade study T-16. Depends on module 1 (stream convention).

## 1. The codes

Quasi-cyclic LDPC codes of the IEEE 802.11n structure: parity-check matrix `H = [Hs | Hp]` built from a base matrix of `mb` block rows and 24 block columns of size `Z x Z`; `Z` = 27 for N = 648 and `Z` = 81 for N = 1944; `kb = 24 - mb` information block columns and `mb` parity block columns; `mb` = 12, 8, 6, 4 for rates 1/2, 2/3, 3/4, 5/6. A base entry is either empty or a cyclic shift `s` (0 to Z-1): the block is the identity matrix rotated so that row `r` has its one in column `(r + s) mod Z`. The parity part `Hp` is the dual-diagonal 802.11n form: the first parity column (block column `kb`) has entries `x` in block row 0, `0` in block row `mb/2` and `x` in block row `mb-1`; block column `kb + c` (c = 1 to mb-1) has shift 0 in block rows `c-1` and `c`.

**Code provenance (important).**
- N = 648, rate 5/6 is the real IEEE 802.11n code: the base matrix was extracted from `WIFI_540_648.alist` of the AFF3CT project (MIT licence; a copy is kept in `tests/13-ldpc-encoder/data/` with its notice) and verified to be quasi-cyclic with Z = 27 and the dual-diagonal parity structure. It is used as the independent cross-check of the encoder.
- The other seven combinations (N = 648 at rates 1/2, 2/3, 3/4; N = 1944 at all four rates) are **own designs** with the same structure, generated by `scripts/gen_ldpc_codes.py` (seeded, deterministic): information columns of degree 3 or 4 (as far as `mb` allows) placed to balance the row degrees, random shifts accepted only if the base matrix stays free of 4-cycles (girth at least 6). The reference sources contain no 802.11n tables and they were not typed from memory. Their error-rate performance is **not** claimed to match the standard's: it is measured against the standard code with AFF3CT (section 5, and SIM-002 for the full study) and the generator can be replaced by the standard tables when they are available.

Code select input `code[2:0]`: bit 2 selects the length (0: 648, 1: 1944), bits 1..0 the rate (0: 1/2, 1: 2/3, 2: 3/4, 3: 5/6). Information length K = (24 - mb) Z (324, 432, 486, 540 for N = 648; 972, 1296, 1458, 1620 for N = 1944).

## 2. Encoding algorithm (systematic, block-serial)

Message `s` = K bits as `kb` blocks of Z bits (block j = bits `jZ .. jZ+Z-1`, bit order within the message LSB first).
1. For every block row i: `lambda_i` = XOR over information columns j with an entry of `rot(s_j, shift(i,j))`, where `rot(v, s)[r] = v[(r + s) mod Z]`.
2. `p_0` = XOR of all `lambda_i` (the dual-diagonal columns cancel pairwise in the sum of all block rows, and the three `p_0` entries sum to the identity).
3. `p_1 = lambda_0 XOR rot(p_0, x)`; for i = 1 to mb-2: `p_{i+1} = lambda_i XOR p_i`, and additionally `XOR p_0` when `i = mb/2`.
4. Codeword `c = [s | p_0 | p_1 | ... | p_{mb-1}]`, N bits, systematic.

(All block rows are used: the sum of all rows gives `p_0` and rows 0 to mb-2 give `p_1 .. p_{mb-1}`; the tests verify `H c = 0` for every row, the last block row included.)

## 3. Interface

Module `ldpc_enc`: `clk`, `rst_n`, `code[2:0]`, input stream `s_axis_*` and output stream `m_axis_*` of 32-bit words carrying a bit string LSB first (bit `b` of the string is bit `b mod 32` of word `b / 32`). Input: K bits in ceil(K/32) words, `last` on the final word; bits above K in the final word are ignored. Output: N bits in ceil(N/32) words, `last` on the final word, the bits above N in the final word are zero. `code` is sampled with the first input word of a codeword. `err_len` pulses when `last` disagrees with the word count (as in modules 4 and 5); the codeword is still closed by the count. One codeword is processed at a time (the input is held off while a codeword is being computed or sent).

Cycle count per codeword: ceil(K/32) load + at most mb x kb accumulate + mb parity + ceil(N/32) output (for N = 1944, rate 1/2: about 31 + 144 + 12 + 61 = 250 clocks, 780 Mbit/s of information at 200 MHz, against the 155 Mbit/s requirement).

## 4. Test plan

Python `LDPC` helper builds `H` from the generated base matrices (`tests/13-ldpc-encoder/ldpc_codes.json`), independent of the RTL tables.

| ID | Test | Pass criterion |
|---|---|---|
| T13-01 | Parity check, all 8 codes | 20 random messages per code: the RTL codeword satisfies `H c = 0` over GF(2) for every row |
| T13-02 | Systematic and framing | The first K bits equal the message; output word count is ceil(N/32); `last` on the final word; unused bits zero |
| T13-03 | Standard code, independent check | The N = 648, rate 5/6 codewords satisfy the parity-check matrix **read from the AFF3CT alist file** (not from the generator) |
| T13-04 | Linearity | `enc(a) XOR enc(b) = enc(a XOR b)` for random pairs; the all-zero message gives the all-zero codeword |
| T13-05 | Handshakes and mixed codes | Back-to-back codewords with a different code each, random valid and ready: all valid codewords; protocol check passes |
| T13-06 | Cycle count | Clocks per codeword are at most 300 for every code with an always-ready sink (measured and recorded) |
| T13-07 | Bad `last` | `err_len` pulses; the codeword is closed by the count; the next one is correct |
| T13-08 | Code design properties (Python, no DUT) | Every base matrix is free of 4-cycles, has the dual-diagonal parity structure, the right dimensions and rate; the 648/5/6 matrix equals the one extracted from the alist |
| T13-09 | Code quality (AFF3CT, run as a script) | Each code decoded with layered normalised min-sum shows a waterfall (frame error rate falls with SNR); results recorded and compared with the standard code in section 5 of the results |
| L-13, S-13 | Lint and synthesis | `-Wall` clean; no latches; counts recorded |

## 6. Open items

- The own-design codes are placeholders until the standard tables are obtained; the generator and the ROM format accept replacements without RTL changes.
- Slice-aligned packing of bytes into K-bit messages and codeword padding (module 16 and the MAC).
- Block-RAM mapping of the message and parity buffers (flip-flops here), and a higher-throughput parallel variant if the clock budget requires it.

### Code quality (T13-09), AFF3CT, measured

Layered normalised min-sum, 20 iterations, BPSK over AWGN, stopping at 40 frame errors or 20000 frames. FER against Eb/N0 (dB):

Reading: every code has a clean waterfall. The own-design 648/5/6 code performs about like the real standard code at the same length and rate (slightly better at 3.5 and 4.0 dB, equal within the statistics at 4.5 dB, where 12 to 14 frame errors were counted), so the design procedure is not obviously weaker than the standard for this case; **this is one comparison, with few errors at the lowest FER, and does not prove equivalence for the other rates and lengths**. The SNR for FER 1e-3 per codeword is about 2.8 dB (R1/2, N = 648), 3.4 dB (R2/3), 3.9 dB (R3/4), 4.5 dB (R5/6) and about 2.3 dB (R1/2, N = 1944); the required FER for the system is 1.2e-5 per codeword (PHY-011), so error floors at much lower FER are still to be studied (SIM-002).

Notes:
- The alist file is the only verified standard matrix available; the first version of the quality script mis-indexed the AFF3CT output columns and missed negative Es/N0 values (fixed).
- The encoder is block-serial and processes one codeword at a time; throughput is far above the requirement, so no parallel variant is built.
